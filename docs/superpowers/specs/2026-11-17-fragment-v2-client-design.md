# Marketo Asset API v2 fragment client (New Email Designer) — SDK design

Scope: `marketo-rest-sdk-java` only. The provider (`marketo-content-provider`) gets its own spec. Ticket: MRKT-510 (SDK part).

## Intent

Emails built in the New Email Designer reference fragments as `{{ fragment id="ajo:<id>" ... }}` inside `html.body`, and the fragment content is a separate asset that the v1 API cannot read: `GET /rest/asset/v1/fragment/ajo:...` returns `610` (MRKT-506, Findings #3). The v2 Asset API serves fragments at `/rest/asset/v2/fragment`. MRKT-510 needs the provider to list and read fragments, so the SDK needs a v2 fragment client with **list (filter)** and **get by id**, the same two operations `MarketoEmailV2Client` got in MRKT-507.

Write calls for fragments (clone, update, create draft, approve) are out of scope here; they belong to the fragment delivery ticket.

## Goals

- A v2 fragment client exposed from `MarketoClientManager`, with `filterFragments` and `loadFragmentById`.
- `filterFragments` supports every filter the Adobe swagger declares for `GET /rest/asset/v2/fragment/filter`.
- No behavior change for any existing v1 or v2 email command or client.

## Non-goals

- No change to `MarketoEmailV2Client`, its commands or its domain classes.
- No client-side validation or clamping of values the API decides (`sortKey`, `pageSize`, `fragmentType`, `scriptEngine`, date range); a wrong value surfaces as the API's error. The only checks are structural, on the SDK's own inputs: the filter builder requires a non-blank `workspaceId`, rejects a null `status` element and copies the `status` list, and `loadFragmentById` rejects an id that is not a plain alphanumeric token (it becomes a URL path segment).
- No provider code, no Smartling-side concepts.
- No shared base class for the v2 commands in this change (see Duplication).

## Facts

Sources: Adobe `swagger-asset.json` (`/rest/asset/v2/fragment/filter`, `/rest/asset/v2/fragment/{id}`), MRKT-506 Findings #3 and #10, and two probe sets on a Marketo sandbox instance on 2026-11-17, all fragment calls with the `x-app-type: marketo` header (one folder lookup used the v1 folder API). The **first** set was read-only GETs (one workspace, 11 fragments in one Design Studio folder and one sub-folder of it); every figure below that counts fragments (11, 5 draft and 6 published) describes that set. ## Open items

The probes settled the date format, the `metadata` date format, the `603` for a missing id, `sortKey`, sub-folders, the page-size clamp and HTTP 200 on errors. What stays open:

1. **`published_with_draft` on fragments** was observed on one fragment only (see Facts). Not observed: a fragment with a draft whose published version was changed, a discarded draft, and other instances. The client sends whatever status strings the caller gives; it does not validate them.
2. **Other instances.** The id format (24 hex characters) and the `metadata` date format were observed on one sandbox instance. The dates are modeled as `Date`, so a different date format on another instance would make Jackson fail the whole response, list and get alike.
3. **`603` is ambiguous.** The API answers a missing id and a missing permission with the same `603`. The client reports it as `ObjectNotFoundException`, and its Javadoc says that a `603` can also be a permission failure.
4. **Untested filters.** `isModifiedByMe` and `isValueNonNullable` were not probed. The client passes them through unvalidated.
5. **Error `711`.** The executor maps `711` to `FolderTypeNotSupportedException`; it did not occur in the probes (an unknown folder and `folderType=Program` for a folder id gave `709`, which stays a plain `MarketoApiException`).

## Design

Patterns as in the email client: **Command** (existing request abstraction), **Builder** (`FragmentV2Filter`), **Facade** (`MarketoFragmentV2Client` hides commands and the executor). No new strategy or factory layers.

### Duplication

The `x-app-type` header and the GET base class already exist in `rest/command/v2/email` (`BaseEmailCommand`, `BaseEmailGetCommand`, both `public abstract` with protected constructors, so a fragment command could extend them). They are email-named, and an email-named base for a fragment command misleads readers. This change adds the fragment copies (`BaseFragmentCommand`, `BaseFragmentGetCommand`) instead of renaming and moving the email ones, so no email class changes and the parallel work on the same SDK (fragment write calls, email templates) does not conflict. Extracting a shared `rest/command/v2` base for the three asset types is a follow-up refactor.

### New types

Package layout follows the email layout: `rest/command/v2/fragment`, `domain/v2/fragment`; the public API keeps the `V2` suffix, the commands do not.

- `rest/command/v2/fragment/BaseFragmentCommand<R>` and `BaseFragmentGetCommand<R>`: as the email ones (header `x-app-type: marketo`, method `GET`, no parameters by default).
- `rest/command/v2/fragment/FilterFragments` — path `/asset/v2/fragment/filter`. Puts only non-null filter values into `getParameters()`, already converted to strings, string values percent-encoded and `status` kept as a list of encoded strings, exactly as `FilterEmails` does (same reasons: the executor sends `toString()`, keeps existing `%XX` and reads `{...}` as a template). Dates go out in UTC as the zone-less date-time `yyyy-MM-dd'T'HH:mm:ss`, whole seconds, exactly as `FilterEmails` sends them (observed to work on fragments, with an inclusive `*Start` and an exclusive `*End`; never date-only, whose `*End` covers the whole day, see Facts). `folderType` is read from the `FolderType` enum's `@JsonProperty` through the SDK's mapper.
- `rest/command/v2/fragment/GetFragmentById` — `BaseFragmentGetCommand<List<FragmentV2>>`, path `/asset/v2/fragment/{id}`.
- `domain/v2/fragment/FragmentV2` — `id`, `name`, `description`, `status`, `state`, `appType`, `externalId`, `virtualId`, `scriptEngine`, `themeId`, `settings` (`fragmentType`, `fragmentSubType`, `supportedChannels`), `metadata` (`createdBy`, `createdAt`, `modifiedBy`, `modifiedAt`; the two dates as `Date`, read by the SDK mapper's `yyyy-MM-dd'T'HH:mm:ss'Z'Z`, which matches the observed format, for example `2026-01-02T03:04:05Z+0000`; see open item 2), `appData` (`workspaceId`, `folderId`), `associatedStates` (a list of `AssociatedState` with `contentId`, `externalId`, `state`, all `String`, the same shape as `EmailV2.AssociatedState`), `data` (`html.body`, `text.body`, `text.syncFromHtml` as a `boolean` like `EmailV2`; null on list items). `settings.supportedChannels` is a `List<String>`. Each nested object is a small static nested class of `FragmentV2`. `associatedStates` and `text.syncFromHtml` are modeled although list and get do not use them, because the fragment delivery work (MRKT-511 finds the draft of a `published_with_draft` copy from the published fragment's `associatedStates`, as for emails; observed on one fragment, see the `published_with_draft` row and open item 1; the draft entry has no `externalId`, so all three fields are nullable `String`s) needs them and the read model then stays in one place. `editorContext` and `thumbnail` are not modeled; `appData.editorContent` (Findings #10) is not in the swagger's `AppDataDTO` and is not modeled either (not needed). Unknown JSON fields are ignored by the existing mapper. Field types are strings except where stated.
- `domain/v2/fragment/FragmentV2Page` — `items`, `totalItems`, `pageSize`, `currentPage`, plus `empty()`.
- `domain/v2/fragment/FragmentV2Filter` — immutable, built with a builder; `workspaceId` is required. Fields and builder names as `EmailV2Filter` (no `is` prefix), with `fragmentType` instead of `templateId`. `workspaceId` is the argument of the factory method `FragmentV2Filter.builder(workspaceId)`, which rejects a null or blank value. The other fields are builder methods:

| Builder name | Java type |
|---|---|
| `folderId`, `name`, `fragmentType`, `scriptEngine`, `valueNonNullable` (wire `isValueNonNullable`, a string in the swagger), `sortKey` | `String` |
| `folderType` | existing `FolderType` |
| `status` | `List<String>` |
| `sortOrder` | existing `SortOrder` from `domain/v2/email`, reused, not copied |
| `createdByMe`, `modifiedByMe`, `includeArchived` (wire `isCreatedByMe`, `isModifiedByMe`, `includeArchived`) | `Boolean` |
| `createdAtStart`, `createdAtEnd`, `modifiedAtStart`, `modifiedAtEnd` | `Instant`, sent in UTC as `yyyy-MM-dd'T'HH:mm:ss`; `*Start` is inclusive and `*End` exclusive on the API side |
| `pageIndex`, `pageSize` | `Integer` |
- `MarketoFragmentV2Client` (in `com.smartling.marketo.sdk`) and `rest/MarketoFragmentV2RestClient`:
  - `FragmentV2 loadFragmentById(String id)` — rejects a null/blank id or one that does not match `[A-Za-z0-9]+` with `IllegalArgumentException` before building the command. This keeps `ajo:<id>` (the form in an email reference), `/`, `?`, `{` and `}` out of the URL path, where they would change the route or be read as a URI template. The pattern is deliberately wider than the observed 24-character hex ids (open item 2). A word such as `filter` matches the pattern; the API answered `GET /fragment/filter` (without `workspaceId`) with `603`, which the client reports as not found, and a unit test pins that the client lets such a word through. Throws `ObjectNotFoundException` when the result is null or empty or its first element has no id (the email client applies the no-id check only to `cloneEmail` and `createDraft`, not to `loadEmailById`; the fragment get applies it because a returned fragment without an id cannot be used), and rethrows error `603` as `ObjectNotFoundException` (a missing id answers `603`, see Facts and open item 3). The Javadoc says the id is the one in the email reference without `ajo:`, and that a `603` can also be a permission failure.
  - `FragmentV2Page filterFragments(FragmentV2Filter filter)` — a null `result` with `success:true` yields `FragmentV2Page.empty()`. Its Javadoc states: the filter dates are sent in UTC as whole seconds, so fractional seconds are truncated, which moves a `*Start` bound down and an `*End` bound down by less than a second (an exclusive `*End` of `T.5` is sent as `T`, which excludes a fragment modified at `T.3`; callers needing exact bounds filter locally); `*Start` is inclusive and `*End` exclusive (observed); `pageSize` has the swagger maximum of 50 and larger values are answered with 50 (observed); a `folderId` also matches sub-folders (observed); and it does not claim anything observed for emails only.
- `MarketoClientManager.getMarketoFragmentV2Client()` and its implementation in `MarketoRestClientManager`. `MarketoRestClientManager` is the only implementer in this repo and in `marketo-content-provider`, where the interface is only used and mocked (checked with grep on 2026-11-17); an implementer outside these two repos must add the method, so the version bump is minor.

### Error handling

As for the email client, the executor's mapping applies to the fragment commands unchanged (`JaxRsHttpCommandExecutor`): rate-limit codes `606`, `607`, `615` map to `RequestLimitExceededException`; `702` and `710` map to `ObjectNotFoundException` (`702` unless its message is an "update content not allowed" one); `711` maps to `FolderTypeNotSupportedException` (not observed for fragments, open item 5); `60019` maps to `EmailContentRejectedException` for every command, a write error that the read-only calls here are not expected to produce; `611`, `709`, `60000` and the other codes stay `MarketoApiException`. Fragment errors are answered as HTTP 200 with `success:false` (observed, see Facts); a non-2xx status would make the executor throw a `WebApplicationException` before this mapping runs, as it already does for v1.

### Versioning

Minor bump in `pom.xml` (3.3.0 → 3.4.0), as its own commit: the interface `MarketoClientManager` gains a method. If the parallel email-template change also claims 3.4.0, whichever merges second takes the next minor version.

## Testing

JUnit 4, Mockito, AssertJ and WireMock as in the email tests.

- `FilterFragments` / `GetFragmentById` command tests: path, method, header, only set filters appear in the parameters (every filter, dates as `yyyy-MM-dd'T'HH:mm:ss` in UTC, including an `Instant` with zero seconds, one with fractional seconds that are truncated (see the `filterFragments` Javadoc note in the Design section), and an `Instant` built from an `OffsetDateTime` with a non-zero offset, `status` list, `sortOrder`, `folderType` sent as `Folder`/`Program`, `fragmentType`, `valueNonNullable` sent as a string, percent-encoding of reserved characters).
- `FragmentV2Filter`: rejects a null/blank `workspaceId`, defensive copy of `status`, an empty `status` list sends no parameter, a null element is rejected.
- Deserialization tests from fixtures `src/test/resources/json/fragment-v2-filter-response.json`, `fragment-v2-get-response.json` and `fragment-v2-get-published-with-draft-response.json`. All three fixtures follow the response shapes observed on 2026-11-17 (see Facts: the item fields, `metadata` dates like `2026-01-02T03:04:05Z+0000`, `settings.supportedChannels`; the get fixture has `appData.editorContent`, the list fixture has `appData.editorType`), with abstract ids, names, bodies and user names and no sandbox data. The list fixture has one item that lacks the optional keys (`description`, `thumbnail`, `editorContext`, `themeId`) and one with `settings.fragmentSubType`; the get fixture has a published fragment whose `associatedStates` entry has its own `id` as `contentId`, and the published-with-draft fixture is for a `published_with_draft` fragment (`state` `published`) with two `associatedStates` entries, the draft one without `externalId` (deserialized as `null`). The tests cover `settings.fragmentType`, `settings.fragmentSubType`, `settings.supportedChannels`, both `metadata` dates as `Date`, `associatedStates` (`contentId`, `externalId`, `state`), `data.text.syncFromHtml`, and that the unmodeled fields (`editorContent`, `editorType`, `thumbnail`, `editorContext`, the `*ById`/`*AepId` metadata keys) are ignored. The list fixture also has a draft item whose single `associatedStates` entry points to itself (`contentId` equal to its `id`, `state` `draft`), so a draft item's `associatedStates` is pinned too.
- `MarketoFragmentV2RestClientTest`: `loadFragmentById` rejects `null`, blank, an `ajo:`-prefixed 24-character hex id, `1/2`, `{a}`, `a?b`; accepts an abstract 24-character hex id such as `0123456789abcdef01234567` and the word `filter`; maps `603` to `ObjectNotFoundException`; empty and null result, and a first element without an id, to `ObjectNotFoundException`; `filterFragments` maps a null result to an empty page, rejects a null filter, and leaves a `603` as a plain `MarketoApiException`.
- One end-to-end WireMock test in package `com.smartling.marketo.sdk.rest`, wired like `MarketoEmailV2EndToEndTest` (a `RetryingHttpCommandExecutor` over the real executor with `RetryPolicy.NONE`, so that `606` surfaces instead of being retried): a `603` from `loadFragmentById` becomes `ObjectNotFoundException`; both requests carry `x-app-type: marketo`; the get request path carries the id and the result's first element is returned; every filter is sent as a query parameter, with the `yyyy-MM-dd'T'HH:mm:ss` date values and repeated `status` parameters on the wire; `611` becomes `MarketoApiException`; `606` becomes `RequestLimitExceededException`.
- Deserialization of a list item with no `data`, and of a `FragmentV2Page` with null `items`.
- `MarketoRestClientManagerTest`: `shouldReturnFragmentV2RestClient`.
