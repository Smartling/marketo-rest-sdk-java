# Marketo Asset API v2 fragment write calls (clone, update, create draft, approve): SDK design

Ticket: MRKT-511 (SDK part). Scope: `marketo-rest-sdk-java` only. The provider has its own spec (`docs/superpowers/specs/2026-11-17-fragment-content-design.md` in `marketo-content-provider`). This spec builds on:

- the email write calls (`2026-11-10-email-v2-write-calls-design.md`, merged as 3.3.0): the `JSON_POST` transport in `JaxRsHttpCommandExecutor` and its `60019` mapping (by code, for every command) are reused as they are. The `603` handling is **not** in the executor: each client reports a missing id itself (`MarketoEmailV2RestClient.executeReportingMissingEmail`), so the fragment write methods go through MRKT-510's `MarketoFragmentV2RestClient.executeReportingMissingFragment`;
- the fragment read side of MRKT-510 (`2026-11-17-fragment-v2-client-design.md`, branch `MRKT-510-fragment-client`, committed, version-bumped to 3.4.0 in `cd1f15f`, with its pull request (#65) not merged when this spec was written; branch head `4d0b59d` "MRKT-510 Finish the style cleanup after the final review", the version bump to 3.4.0 being the earlier commit `cd1f15f`): `MarketoFragmentV2Client` with `filterFragments` and `loadFragmentById`, the `FragmentV2` model (with `associatedStates` and `data.text.syncFromHtml`, verified on that branch), `BaseFragmentCommand`, `BaseFragmentGetCommand`. This change adds methods to that client and does not redefine any of it.

**Branch base.** The implementation branch is based on `MRKT-510-fragment-client` (or on `master` after MRKT-510 merges), not on the `master` the worktree was created from, which has no fragment client. The plan's first task rebases onto it. This work depends on MRKT-510, so it merges after it and its version bump is `3.5.0`. MRKT-510 was not merged when this spec was written: if its history is squashed or amended when it merges, this branch is rebased again onto the result.

## Intent

Delivering a translation of a fragment needs the four write calls that `MarketoFragmentV2Client` does not have: clone the source fragment into a language copy, update a draft, create a draft of a published copy, and approve a draft.

## Goals

- `MarketoFragmentV2Client` gets `cloneFragment`, `updateFragment`, `createDraft` and `approveFragment`.
- Nothing changes for any existing v1 or v2 command, except that the class thrown for error `60019` is renamed (see Errors).

## Non-goals

- No change to the transport (`JSON_POST` exists since 3.3.0), to `MarketoEmailV2Client` or to any email class, except the rename of `EmailContentRejectedException` to `ContentRejectedException` (see Errors), which touches the class, the executor, one Javadoc link of `MarketoEmailV2Client` and three existing tests. The Javadoc of `MarketoFragmentV2Client`, whose class comment says "read-only", is updated to cover the write methods.
- No fragment delete, unapprove, discard or other state transitions; no `usedby`.
- No client-side validation of values the API decides (names, HTML). Only structural checks on the SDK's own inputs: ids, a non-null `name` and a non-null update with at least one part.
- No provider code and no Smartling concepts.

## Facts

Observed on the Smartling sandbox on 17 November 2026 (read and write calls by hand, API user of the sandbox token; the source fragment was cloned in the Marketo UI because the API clone is refused, see below), except the two rows that cite MRKT-506 Findings #10 (28 October, the fragment API clone and its `60000` answers). Values in the provider spec's fixtures are abstract; ids here are not recorded. The paths, request bodies and the response shape (`result` is an array of the fragment) are also declared by Adobe's `swagger-asset.json` (`/fragment/clone`: `CloneAssetRequest`; `/fragment/{id}/update`: `UpdateFragmentRequest`; `/fragment/state/transition`: `StateTransitionRequest` with `action` one of `approve`, `unapprove`, `discard`, `create_draft`; all three answer `FragmentNewResponse`); rows below say "observed" only for what the sandbox calls showed.

| Call | Observation |
|---|---|
| Clone through the API | `POST /rest/asset/v2/fragment/clone` with `{"assetId", "newAsset": {"name", "description"}}` answered `603 Access denied` (HTTP 200, `success: false`), as the v2 email clone did for this user on the same day (the email write-call spec records, from the Marketo audit trail, that the same user cloned new-editor emails through the API until 30 October). MRKT-506 Findings #10 (28 October, before the API clone stopped working) records that the fragment API clone with `{assetId, newAsset: {name}}` creates a copy "in the same folder, `draft`". No response body of a fragment clone was recorded, so the clone response shape is the schema's (`FragmentNewResponse`) and the clone fixture is synthetic (Testing). A copy made in the UI is a `draft` with an empty description, its own id and `associatedStates` holding only its own draft entry. |
| Update | `POST /fragment/{id}/update` with `{"data": {"html": {"body"}, "text": {"body"}}}` on a draft: HTTP 200, `result` is an array with the fragment. The new bodies are read back by a get. |
| Update, text body | An update that sends only `data.html.body` leaves `data.text.body` as it was, although `data.text.syncFromHtml` is `true`: the text body is not regenerated. |
| Update, damaged markers | An update of a draft whose HTML had damaged markers (`{lead.First Name:default=friend}}`, `{{!- ... --}}`) was **accepted**. `60019` was not seen for damaged markers on fragments (the email write-call spec says of its own damaged-markers cause that it "is inferred from before/after pairs"). |

| After approve, draft of a published fragment | In case (2) the former draft id no longer exists: a get of it and an update of it answer `60051` ("Content Wave Asset Has Been Deleted"), and an approve of it answers `60000` ("Content Wave Asset Not Found Or Deleted"). Case (1) has no separate draft id to read. |
| Approve of the published id while a draft exists | `60000` ("Content Wave api failed"); the draft stays and the published content is unchanged. Approve works only on the draft id. |
| Update of the published id of a published fragment with no draft | `60019` (`contentWaveAssetUpdationFailed`); the content is unchanged. |
| Create draft | `POST /fragment/state/transition` with `{"contentId": <published id>, "action": "create_draft"}`: `result` is an array with the draft: its own `id`, `status` `published_with_draft`, `state` `draft`, and `associatedStates` with the published entry (`externalId` present) and the draft entry (`state` `draft`, `contentId` equal to the draft's `id`, no `externalId`). A get of the published id and a get of the draft id both return `status` `published_with_draft` and the same two entries. |
| Create draft when a draft exists | `60000` ("Content Wave api failed"), as for emails. |

With `status=published_with_draft` it is returned; with `status=draft` or `status=published` the result is empty. |
| Filter sort key | `sortKey=name` with `sortOrder=ASC` and `pageSize=50` is accepted; an unknown sort key answers `611`. |
| Folder of a copy made in the UI | The copy has the same `appData.folderId` and `workspaceId` as its source. |

| `settings` of the sandbox fragment | `fragmentType` `visual` and `supportedChannels` `["email"]`; there is no `fragmentSubType`. |
| Duplicate name, name over 100 characters | `60000` with no other detail, for the fragment API clone (MRKT-506 Findings #10, 28 October). |

## Design

Patterns as in the email write calls: **Command**, **Facade**. One variant, one caller, no new layers.

### New commands (`rest/command/v2/fragment`)

| Command | Path | Body |
|---|---|---|
| `CloneFragment` | `/asset/v2/fragment/clone` | `{"assetId", "newAsset": {"name"}}` (no description: the email clone ignored it in one call, and no fragment clone response was recorded) |
| `UpdateFragment` | `/asset/v2/fragment/{id}/update` | from `FragmentV2Update`: `data.html.body` and `data.text.body`, each omitted when unset, with `data.html` or `data.text` omitted when its `body` is unset. `data` is always sent: the builder rejects an update with no part, so `data` is never empty (the email command also has `headers`, which is why it needs an empty-object rule and this one does not). |
| `TransitionFragmentState<R>` | `/asset/v2/fragment/state/transition` | `{"contentId", "action"}`; `action` from the enum `FragmentV2StateAction { APPROVE("approve"), CREATE_DRAFT("create_draft") }`, put in the map as its API value (a String). A private constructor and two static factories, as `TransitionEmailState`: `approve(id)` with the result type `Void.TYPE` and `createDraft(id)` with `List<FragmentV2>`. |

They extend a new `BaseFragmentPostCommand<R>` (method `JSON_POST` and body rules as `BaseEmailPostCommand`; the `x-app-type` header is inherited from `BaseFragmentCommand`), which itself extends MRKT-510's `BaseFragmentCommand<R>` (the email pattern: `BaseEmailPostCommand` extends `BaseEmailCommand`; the constructor of `BaseFragmentCommand` is protected, which a subclass can call). `FragmentV2Update` and `FragmentV2StateAction` live in `domain/v2/fragment`, next to `FragmentV2Filter`. `FragmentV2Update` is a `final` class; `FragmentV2StateAction` is a public enum with a public `getApiValue()`, as `EmailV2StateAction`, because the command in another package reads it. The email commands are not reused, because their base classes are email-named (the same reason MRKT-510 gives for its read side). Extracting shared v2 bases is a follow-up refactor.

### Client methods

On `MarketoFragmentV2Client` and `MarketoFragmentV2RestClient`:

- `FragmentV2 cloneFragment(String id, String name)`: returns the new fragment. The command's result type is `List<FragmentV2>` and the client returns the first element; a null or empty `result`, or a first element without an `id`, throws `ObjectNotFoundException` with a message naming the operation and the source id (as `cloneEmail`). The null, empty and no-`id` checks go into one private helper `firstFragmentWithId(list, message)` of `MarketoFragmentV2RestClient`, as the email client's `firstEmailWithId`, used by clone and `createDraft`. `loadFragmentById` is left unchanged: it has two different messages (an empty result, and a first element without an `id`), which a single-message helper cannot keep.
- `void updateFragment(String id, FragmentV2Update update)`: `FragmentV2Update` is immutable with a private constructor, getters and `FragmentV2Update.builder()`, with the optional parts `htmlBody` and `textBody`; a `null` part is not sent, an empty string is sent as is. `build()` rejects an update with no part set (`IllegalArgumentException`). `syncFromHtml` is not sent. The Javadoc says the text body is not regenerated from the HTML, so a caller that changes the HTML sends the text body too.
- `FragmentV2 createDraft(String id)`: returns the draft (its own id). Result handling as for clone. The Javadoc says a published fragment that already has a draft answers `60000`.
- `void approveFragment(String id)`: `id` is the id of the **draft** to approve: the id of a `draft` copy (observed with a copy made in the UI, which stood in for the clone, because the API clone was refused on 17 November) or the draft of a `published_with_draft` fragment (observed). Approving the published id of a `published_with_draft` fragment answers `60000` and changes nothing (observed). Result type `Void.TYPE`, like `approveEmail`. The Javadoc says that the id of a draft created from a published fragment stops existing after the approve (a get or update of it answers `60051`, an approve of it `60000`; one observation each); for a never-published draft (a copy made in the UI) the same id became the published one (one observation).

`updateFragment` and `approveFragment` use `Void.TYPE`, for the reason given in the email write-call spec (a write that Marketo applied must not fail afterwards in deserialization). Id checks: every `id` goes through MRKT-510's existing private helper `requireAlphanumericId` of `MarketoFragmentV2RestClient` (not null, not blank, `[A-Za-z0-9]+`), which `loadFragmentById` already uses; a null `name` or null `update` is a `NullPointerException` naming the argument; checks run in argument order. Every call goes through `executeReportingMissingFragment` for the `603` mapping below.

### Errors

- `60019` is mapped by code in the shared `JaxRsHttpCommandExecutor` (it is in its code list today, "Email content update rejected"), so a rejected fragment update would arrive as `EmailContentRejectedException`, a name that is wrong for fragments. **Decided by the author: rename it to `ContentRejectedException`** (same package `com.smartling.marketo.sdk.rest`, same two constructors, still a subclass of `MarketoApiException`, still not retried), with no deprecated subclass kept: a subclass thrown by the executor would be the wrong name again, and one that is not thrown would make old `catch` blocks stop catching silently. The rename touches, in the SDK: the class file, `JaxRsHttpCommandExecutor` (its import, the code list constant `EMAIL_CONTENT_REJECTED_CODES`, which becomes `CONTENT_REJECTED_CODES`, together with the local variable `emailContentRejectedError`, which becomes `contentRejectedError`, and the code list comment "Email content update rejected", which becomes "Content update rejected", and the `new` at the mapping), the `{@link}` in the Javadoc of `MarketoEmailV2Client`, and three existing tests (`MarketoEmailV2EndToEndTest`, `MarketoEmailV2RestClientTest`, `JaxRsHttpCommandExecutorTest`, whose test name `shouldMapCode60019ToEmailContentRejectedException` is renamed). Its Javadoc is reworded for both assets. It says today: "when the content of an email update is rejected, for example because of damaged template markers, and also when a published (non-draft) email is updated directly". The new text keeps both clauses for emails (the first is the email spec's inference), says that for fragments the observed cause is the second clause (an update of the published id, with or without a draft; damaged markers were accepted on a draft), and the Javadoc of `updateFragment` says the same; a test pins that a fragment update's `60019` arrives as `ContentRejectedException`. This is a breaking change of a public class introduced in 3.3.0 (MRKT-508) inside a minor bump to 3.5.0 (the author accepts this: earlier minor bumps added interface methods, which break implementers, and a class rename is a different kind of break); the only consumer known here is the provider, which adopts the new name in the same change that pins 3.5.0 (see the provider spec); other consumers of 3.3.0 or 3.4.0 were not checked (Open questions). Earlier design specs (`2026-11-10-email-v2-write-calls-design.md`, and MRKT-510's `2026-11-17-fragment-v2-client-design.md` on its branch) keep the old name in their text: they are historical records, and MRKT-510's file is not touched by this change.
- `603` from `cloneFragment`, `updateFragment`, `createDraft` and `approveFragment` becomes `ObjectNotFoundException` with Marketo's code and message, through `executeReportingMissingFragment`, as the email client does: a get, an update, an approve and a create draft on a missing id answer `603` for fragments (Facts); a clone of a missing source id was not run, and the clone's `603` today is the permission refusal. `603` is also what the API clone answers today to this user, which is a permission failure, so after this change that refusal will reach callers as "not found". The Javadoc says that `603` can be a permission failure, and that a caller must not read an `ObjectNotFoundException` from `cloneFragment` as proof that the source fragment is missing (the caller is expected to have read the source before it clones; the provider spec does). This is accepted for the same reason as for emails (deterministic, not retried), and listed under Open questions.
- As for emails, the error message of a `JSON_POST` holds the method and the path but not the body, so an error from clone or approve (whose ids are in the body) does not name the id; callers add their own context.
- `60000` (a draft that already exists, an approve of the published id while a draft exists, an approve of a draft id that was already approved: all observed; a duplicate or too long name: MRKT-506 Findings #10) and `60051` (a get or update of a draft id after its approve, one observation) stay plain `MarketoApiException`; the Javadoc words them as "observed". `createDraft` takes the id of a published fragment, which is what its Javadoc says; the provider calls it for nothing else.
- Rate limits (`606`, `607`, `615`) are retried as for any command. Only `RequestLimitExceededException` is retried by the SDK, and it comes from an answer that refused the request; a second copy from a retried `cloneFragment` would need a first request that was applied and still answered with a rate-limit error. The provider looks the copy up by name before it clones, as for emails.

### Model

`FragmentV2.getAssociatedStates()` and `data.text.syncFromHtml` come from MRKT-510 (`AssociatedState` with `contentId`, `externalId` and `state`, all strings, nullable; `syncFromHtml` a `boolean`); both are verified on its branch at its head `4d0b59d`. This change does not model them.

### Versioning

Minor bump in `pom.xml` to `3.5.0`, as its own commit: `3.4.0` is MRKT-510's (its branch already carries "Release 3.4.0") and this change depends on it, so it merges second. If another change (for example the email template client) were to take `3.5.0` first, this one would take the next minor version.

## Testing

JUnit 4, Mockito, AssertJ and WireMock as in the email tests.

- Command tests: path, method, headers (`x-app-type: marketo`) and the exact JSON body of each command, including omitted `null` parts and the omitted `data.html` or `data.text` object; the `action` is sent as its API value; cases that set only `htmlBody` (the text body is not sent), only `textBody` and both parts, to pin that `syncFromHtml` is never sent and that the text body is never derived from the HTML.
- `FragmentV2Update`: `build()` with no part set is rejected; an empty string counts as set.
- `MarketoFragmentV2RestClientTest`: each method delegates with the right command; id checks (`1/2`, `{a}`, `ajo:<id>`, empty, blank (`"  "`), null) on every `id`; a null `name` and a null `update`; the argument order of the checks (`cloneFragment(null, null)` throws `IllegalArgumentException` for the `id`, not `NullPointerException` for the `name`); clone and `createDraft` with a null or empty `result` and a first element without an `id` throw `ObjectNotFoundException`; `603` from each of the four write methods becomes `ObjectNotFoundException` with Marketo's code and message; a `ContentRejectedException` thrown by the (mocked) executor passes through unchanged (the by-code `60019` mapping for fragments is pinned only by the end-to-end test below); `60000` and `60051` are plain `MarketoApiException`.
- Command tests also cover both transition actions (`approve` and `create_draft`) with their exact bodies.
- Deserialization: the create-draft fixture `fragment-v2-create-draft-response.json` (draft entry whose `contentId` equals the draft's `id`, no `externalId`) and the clone fixture `fragment-v2-clone-response.json`, in `src/test/resources/json/` next to MRKT-510's fragment fixtures. The clone fixture is built from the swagger schema (`FragmentNewResponse`, whose `result` is an array of `FragmentDetailDTO`) and the fields of the UI-cloned copy observed on the sandbox, because the swagger has no clone example for fragments and no fragment clone response was recorded. The clone fixture is therefore synthetic: the clone deserialization and end-to-end tests only prove that this assumed shape parses, not that Marketo answers with it. Both use abstract ids and names.
- End-to-end WireMock through the real manager, in MRKT-510's `MarketoFragmentV2EndToEndTest`, one test per call: request path, headers and JSON body; update and approve succeed with an array `result` and with no `result`. That test's `newClient()` takes no argument and hardcodes `RetryPolicy.NONE`, so it becomes `newClient(RetryPolicy)` as in `MarketoEmailV2EndToEndTest` (with `setUp` passing `NONE`), and the tests about retries use a second client built with an `ExponentialBackOffRetryPolicy`: `60019` on update becomes `ContentRejectedException` and is not retried (verified with that retrying client and a request count of 1; the email test `shouldMapError60019OnUpdateToEmailContentRejectedAndNotRetry` (its name keeps "Email", it tests an email call; its assertion changes to the renamed class) runs on its `RetryPolicy.NONE` client and so does not exercise retries, which is not repeated here), and a rate-limit error `606` on approve is retried (as the email `shouldRetryApproveAfterError606`).
- Not added: a live integration test.

## Open questions

- A permission failure on clone (`603`) reads as "not found" after the mapping. Decided for this change: `cloneFragment` maps `603` like the other writes, as the email client does (consistent with "like emails").
- Whether `60051` should become a dedicated exception (it is deterministic, but the provider's retry classifier retries a plain `MarketoApiException`). Not decided: only one observation.
- Consumers of the SDK other than the provider that catch or mention `EmailContentRejectedException` (3.3.0 and 3.4.0): not checked; code that catches `MarketoApiException` is unaffected by the rename; code that names the old class stops compiling. The provider's own uses are listed in the provider spec.
